How Events work

An event is the booking hub for a catering job. Staff plan it, attach a menu, generate prep work, run the day, then close the books. This page shows the real screens in Capsule, what each one should show, and how events connect to prep lists, dishes, and the rest of the app.

Typical day-to-day path

From client interest to closed books

This is the path most sales and ops staff follow. Each box is a place you can click in the left nav or from links on the event.

1. Win the job Client record + proposal accepted in CRM. /clients · /clients/proposals
2. Create event New booking with client, date, headcount, venue. /events/new
3. Event home Setup checklist, revise basics, guests, stock, equipment. /events/:id
4. Menu & prep Pick dishes → prep lines + stock holds appear. /kitchen/event-menu · /kitchen/prep
5. Run & close Execute day → complete → finance closeout / invoice. /finance/closeout · /finance/invoices

Create event

/events/new

Register a booking. Requires an active client and venue, plus schedule, headcount, primary contact, and pricing. Can arrive with ?clientId= from an accepted proposal, or ?templateId= from templates.

  • After save → opens that event’s detail page
  • Create encrypts contact fields. If production shows only “Server Error”, the cloud Convex deployment is usually missing CONVEX_FIELD_ENCRYPTION_KEY (set with bunx convex env set … --prod, then bunx convex deploy). Local env does not fix Vercel.

Stage machine

Which buttons show at each stage

Buttons come from proven Manifest stage transitions. The UI only offers moves that are allowed from the current stage.

Planning→ Pending approval→ Approved→ Executing→ Completed→ Closed out · Cancelled
Stage Primary button(s) Also available Editing rules
Planning Submit for approval Cancel event (reason required) Basics revisable; headcount revisable
Pending approval Approve Return to planning · Cancel Basics revisable; headcount revisable

Executing Complete Cancel Basics locked; headcount still revisable; stock panel on

Cross-app map

How the event talks to other pages

The event page is the hub. Other workspaces either deep-link into an event, or read the same event id to show related work.

Outbound from event Inbound to event Shared by event id
Clients & CRM
↔
Client name on the event header links to /clients/:id. Accepted proposals offer “create event” with client prefilled (/events/new?clientId=…. Client communication panel sits on the event itself.
Kitchen · Event menu
→
Setup readiness “Add dishes” goes to /kitchen/event-menu?eventId=…. There you select dishes / apply a menu template. That creates EventDish rows and syncs prep tasks + inventory reservations.
Kitchen · Prep
↔
Prep board at /kitchen/prep lists prep tasks by event. Each task belongs to an event (and usually an event dish). Home attention and notifications can deep-link here when prep is blocked or waiting.
Kitchen · Dishes / menus
→
Catalog dishes and menus live under /kitchen/dishes and /kitchen/menus. They become event-specific only after Event Menu selection. Allergen matrix and allergen briefing read those event dishes.
Staff roster
→
Setup readiness “Assign staff” sends you to /staff/roster. Assignments show up in BEO PDF staffing and setup readiness counts.
Inventory
↔
Event Menu sync creates ingredient demand + reservations. Event Inventory panel (approved/executing) reserves, confirms, and issues stock. Broader stock books live under /inventory/*.
Logistics
↔
Route planner stops reference event ids and show event titles. Plan vehicles/day under /logistics (route planner).
Finance
↔
After Complete, use Close out on the event, then capture/finalize money on /finance/closeout. Invoices can deep-link with /finance/invoices?eventId=…. Tips, payroll, food-cost, and margin reports also key off event closeouts.
Client portal
→
Share control on the event header. Guests/clients can open a portal view at /portal/events/:token.
Production chain

Events ↔ dishes ↔ prep lists

This is the most important handoff. The event does not hold a free-form grocery list — dishes drive prep, and prep drives the kitchen day.

1. Catalog exists first

Chefs maintain reusable dishes (and optional menu templates) in Kitchen. Recipes and dish tasks define how a dish is made.

/kitchen/dishes · /kitchen/menus

2. Attach dishes to the event

On Event Menu, pick an event, optionally apply a menu template, then select dishes and servings. That writes EventDish rows for that booking.

/kitchen/event-menu?eventId=…

3. Prep lines appear

Selecting dishes syncs generated prep tasks (and stock holds) for that event. On the Prep board you can also add manual prep tasks against an event dish, set dependencies, run quality checks, and comment.

/kitchen/prep

4. Event page watches readiness

Setup readiness shows whether menu dishes and staff are in place. Until dishes exist, prep/demand automation has nothing to derive.

/events/:id → Setup readiness
Mental model

One booking, three layers

  • Event When, where, who, stage, money, day-of ops.
  • EventDish Which catalog dishes (and servings) are on this booking.
  • PrepTask Concrete kitchen work lines tied to the event (and usually a dish), with status, station, deps, QC.
What staff should do
Open the event → clear Setup readiness gaps → use Add dishes → then open Kitchen → Prep to work the sheet. Download BEO from the event when you need a printable packet of menu + timeline + staff.
Common confusion
The event detail page does not contain a full dish picker or prep board. If someone expects “menu” and “prep” tabs on the event itself, send them to Event Menu and Prep under Kitchen — that is intentional current wiring.
